# 战术角色认领 · 需求讨论

2026-11-02；任务：[HC-051](../tasks/HC-051-tactic-role-design.md)。用户明确整体替换旧能力标签配置和自动推荐，改为选战术后球员认领本套职责，并覆盖所有现有与后续新战术。本文为新方案设计，正式1.26.0尚沿用旧流程。

## 目标与非目标

目标流程：创建球队基本身份 → 浏览/选择战术 → 查看本队各职责的具体任务 → 指定/认领队员 → 按本队演练。保留本地球队档案、姓名/球衣号码/NBA球队风格、多档案、全部内置动画、3v3/4v4与离线APK。移出体型/能力自评、擅长弱项及自动排名/自动分工产品流程。

不引入在线抢位、多用户同步、自动生成战术或个人Play编辑。将来全场/5v5可以按实际人数扩展，本轮不宣称已支持。角色描述按本套实际配合编写，不把队员永久绑定为控卫/中锋。

## 全覆盖的数据要求

每套战术随自身定义提供角色元数据：稳定roleId、动画棋子ID、短名称、整套配合的一句话职责、角色定义版本。关键阶段提示stepHints可选，填写后必须对应合法步骤/本队角色；不要求每名球员在每帧重复填文案。进攻对应本队attack，防守对应本队defense；对手只是示范。一个角色可在不同阶段执行不同动作，完整职责应覆盖该变化，不能只按第一步站位命名。相似功能可用职责号/初始方位区分显示，身份仍按稳定ID。

每套角色集合与全部帧中本队棋子集合一一对应：人数一致、无缺项/重复/跨阵营、棋子ID稳定存在；球和无主跑位线不是独立角色。文字名仅供显示，绑定按稳定ID，不能依赖数组顺序、球衣号码或可改昵称。

新增战术必须同时交付动画、全部本队角色及整套职责，统一验证从同一战术目录枚举全部注册战术，不能维护一份会漏项的手动白名单。缺角色/无对应棋子/人数不符/空职责/版本无效时，检查失败，不能作为完整可认领战术发布；不自动回退为仅“1号/2号”来掩盖漏配。该检查必须进入实际npm run build和android:build入口；目前Android脚本不会调用npm test，只新增单元测试不足以成为发布门槛。自动检查保证结构，独立内容审查核说明与实际掩护/传球/轮转一致。

## 球队分工与动画

保存按球队ID＋战术ID＋角色定义版本分组的roleId→成员ID分配。一名成员不能在同一套战术兼占两位；职责未认领时明确空位，可以继续看通用示范，不能显示“按本队演练已就绪”。换战术可用另一套分工，不改变队员身份。已认领角色调整应明确交换/解除，避免重复或悄悄挤走别人。

战术改名、目录重排和纯文案修改不改变稳定角色ID；角色身份/棋子绑定、人数或职责语义实质改变时提升角色定义版本，保留旧分工待重新确认，不自动套给新角色。结构变更可由校验辅助识别，语义改变仍须内容审查。更换成员或删除球队只影响对应引用；修改昵称/号码用成员ID继续关联，不以球衣号冒充动画职责号。

档案revision继续用于并发写保护和当前来源一致性；认领有效性单独依据稳定成员ID与角色定义版本，不能因纯昵称/号码修改让所有已认领分工失效。当前session任何update都会提高revision并清来源，这部分需要正式实现时明确调整并测试。

## 迁移与模块边界

旧档案保留球队和成员稳定ID/姓名/号码/球队风格；能力标签退出UI/推荐，原文在可靠迁移前保留备份，不按旧标签替用户确认新职责。现有推荐来源playbackContext不能当作手动认领已确认。继续先读后写、未知版本锁写、调用时快照/串行保存、写失败不表面成功和旧Play/内置选择格式兼容。

存储schema/键的具体升级或旁路策略、原子切换与失败重试需在实现前另定并测试，不在本次讨论直接变更。角色与校验放data/shared，页面只呈现和发起认领，platform/storage职责保持原边界；不将DOM/本地存储依赖放shared。

已核实现约束：shared/templates当前解构只转发固定字段，部分helpers也是位置参数接口；validateLineup也会裁掉未声明字段，仓库/session限进攻推荐来源。因此不能仅给单套文件或旧profile随意追加roles字段；后续必须统一模板透传、纯校验、进攻/防守来源和可靠迁移。旧能力文本可用于迁移前原文备份，不能继续作为新流程的隐性排序/自动认领依据。

## 验收方向

全部现有战术逐套对应角色，实际人物ID/阵营/帧一致；以后添加或删除/重排模板也由同一遍历检查覆盖。负例包括缺/重角色、空任务、错阵营、悬空棋子、重复成员和旧版本失效。正例包括未认领通用播放、三/四人完整认领、两套不同分工、成员改名不失联与能力标签无需填写。

最终需独立内容审查、真实浏览器分工/切换/动画及迁移读写故障、APK和手机分开验收。本轮只做只读清点与设计记录，不构成这些实现验收已完成。

用户担心分工过细导致只跑一套战术。主控提出：先确定本次上场成员与动画编号，切换同人数战术时默认沿用身份对应，展示新战术具体职责，必要时显式交换。用户要求先出图，[HC-052](../tasks/HC-052-tactic-role-flow-concept.md)以三屏说明该候选，并不表示用户已批准沿用规则或放弃逐战术覆盖。

图中采用小王/球衣7号对应动画1，小李/12号对应2，小张/30号对应3；高位挡拆与传切中的任务随模板变化。后续需讨论默认沿用是否需要确认、战术单独调整如何记忆、跨进攻/防守与人员变化的有效性；不得把未确认的默认对应显示为已由球员认领。正式代码/数据与手机仍保持1.26.0。

## HC-053 · 战术条件与确认候选

用户进一步要求能知道适合哪些战术，指出有些配合依赖球员特点。仅默认沿用编号不足以判断适配；主控修正提案为保留帮球队找战术的用途，以本套具体动作条件取代宽泛能力自评或只凭中锋/身高标签判断。用户要求[HC-053](../tasks/HC-053-tactic-requirements-concept.md)先出效果图，筛选/排序算法和入口布局仍待讨论。

候选流程：看这套需要什么→确认队里是否有人能完成→指定承担者→按本队试练。条件状态区分有人可以/还不确定/暂时没有；不确定不能当一般或已满足，选择想担任也不等于已验证具备能力。缺少信息时展示适用条件/先试练，不断言最适合、胜率或专业评估；根据未满足项查其他候选的具体规则尚未实现。

图示采用现有高位挡拆的真实职责概览：持球借掩护并观察传球、站稳掩护后顺下接球、弱侧拉开接应。示例先确认小王/小张，掩护顺下待确认；选小李且确认其能承担后，三人分工才显示可本队试练。球衣7/12/30与动画职责1/2/3保持区分；同一人不能被当作同时满足两个场上位置。可选先看通用示范，未知状态保留。

HC-051的全26套/91职责位覆盖、稳定身份、进攻/防守阵营和未来新增构建检查目标继续有效；本轮不恢复旧擅长/弱项打分，不动真实推荐/存储或APK。

已交付[条件→确认→试练三屏图](../../artifacts/design/tactic-requirements-concept/overview-v1.png)，[提示词](../../artifacts/design/tactic-requirements-concept/prompt.txt)保留。该候选已表达三态和具体动作，尚未获用户对最终交互的批准；生成球场/小刻度不能作为人数或模板数据验收。HC-051“整体替换”仍指旧能力自评及自动分工流程，后续以本节继续讨论保留按具体条件帮助选战术的用途。

## HC-054 · 已批准的正式实现

2026-11-02用户以“可以”批准HC-053，任务进入[HC-054](../tasks/HC-054-role-requirements-release.md)。本节替代上文设计阶段的“未实现/待批准”状态。现行流程是基本建队→选战术→逐项具体条件→三态与成员认领→本队演练，不跨战术自动确认。

所有26套/91位职责已与单套战术定义共置，roleVersion=1；data/templates统一注册，npm build和Android构建入口都校验人数、稳定ID、阵营及每帧棋子。shared/tactic-roles.js只处理角色与三态，未选状态是unknown；available必须有唯一现有成员，missing和unknown不绑定。旧标签和自动加权排名实现及专属排名测试退役，保留原动画、读写保护和新增替代测试。

条件主卡替换战术库内部区域，底栏不增加页。更衣室“找适合本队的战术”与展开战术卡“查看条件”都可进入；条件页可选择全部攻防战术，无同人数球队时明确引导选队，仍可通用示范。角色面板450ms浮起，三态、具体动作和未占用队员选择均在其中；确认失败保输入，成功才关，取消无写盘。交换需明确确认双方新的动作要求。暂无人员时按缺少动作找同人数同攻防且不含这些动作的其他候选，标明仍需确认；没有候选不虚构兜底排名。

持久化沿用halfcourt-lineups-v1键，schemaVersion升级2：profiles/activeProfileId/rolePlans/playbackContext。每队每套计划含templateId/roleVersion/assignments[{roleId,status,memberId}]。来源source=role-confirmations，包含球队ID/revision和模板ID/roleVersion，必须完整有效。确认、交换、重置捕获调用时球队身份及expectedRevision，串行成功才更新状态并递增revision、清旧来源。基本改名/号码保成员ID关联与合法来源，替换成员解除相关位；换队或手选战术可靠解除旧来源后才能切换。

schema1成功读取后只内存迁移，不立即写盘；首次新版写入前精确备份旧原文，失败不覆盖；保球队及成员ID、姓名、号码、NBA风格，旧标签不转新确认、旧自动来源清空。过期roleVersion原计划保留待用户显式重置，首次后续写前备份原文；未知schema和读取失败锁写，损坏条目隔离并保原文，保存快照/队列/重试保持。完整证据及设备边界以任务和独立审查为准。

## HC-055 · 整体体型挑选战术候选

用户体验1.27后要求三个问题一起讨论：找战术选单重设计、3v3球队入口不能出现4v4、按球队整体体型先分类并减少逐个角色选择。用户确认按体型与入口命名「挑选战术」，本轮要求先看效果图。主控提出更衣室→选择阵容类型→对应战术的三屏；3v3候选为一大两小/两大一小/体型接近，4v4候选为一大三小/两大两小/三大一小/体型接近。不把体型自动等同内外线位置或技能，角色安排随动画讲解，分类不代表专业适配结论。

[HC-055](../tasks/HC-055-body-type-tactic-concept.md)已交付[静态图](../../artifacts/design/body-type-tactic-concept/overview-v1.png)：入口按钮新名称、纯体型卡片、仅3v3上下文的玻璃战术选单/现有名称示例。更衣室入口随当前队过滤人数；独立战术库仍可自由浏览不同人数，这一差异需后续实现明确。球队档案是否保存整体体型、分类与战术的逐项映射、取消三态门槛后的旧来源/图例迁移均待正式任务细化，不对旧rolePlans做删除或重解释。效果图尚未获最终视觉批准，HC-054生产流程及手机1.27.0未改。
