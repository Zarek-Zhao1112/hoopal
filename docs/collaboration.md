# 多 agent 协作流程

建立日期：2026-10-22。项目统一约束以 [AGENTS.md](../AGENTS.md) 为准。

## 角色与职责

| 角色 | 负责 | 交付 |
| --- | --- | --- |
| 主 agent | 范围、接口、分工、共享配置、集成、状态和交付 | 任务合同、集成实现、验收结论 |
| 产品 / 设计 agent | 使用流程、战术表达、手机操作和异常边界 | 设计建议与可实现的验收条件 |
| 实现 agent | 指定模块及对应测试 | 代码、测试结果、限制和交接说明 |
| 独立审查 agent | 检查集成结果，复现问题并确认修复 | 审查记录与复验结论 |

角色按任务需要分配，不固定人数或模型。一个 agent 可在不同任务承担不同角色，但不把作者自查当作该改动的独立审查。

## 文档与代码的分工

- 设计文档写“为什么这样做”，给出接口和边界。
- 任务文档写“这次具体做什么、由谁做、如何验收”。
- 代码与测试体现实际行为；发现与文档不一致时，确认用户目标后修正并同步记录。
- 审查文档写“查了什么、发现什么、是否修复、哪些没有验证”。

小型文字修改可以直接完成并检查链接。跨模块功能应有可追踪的设计、任务和审查记录；这些记录用于推进工作，不额外增加用户审批步骤。

## 一次功能迭代

1. 主 agent 明确用户目标、当前状态、范围和验收，建立任务编号。
2. 阅读相关设计；新能力或接口变更补充设计。适合并行的部分拆为有文件边界的工作包。
3. 向实现 agent 下发任务合同。依赖方先约定接口，再并行实现；共享配置与依赖安装统一处理。
4. 实现 agent 在约定目录修改，运行适当检查，并提交交接说明。
5. 主 agent 汇总和集成，处理接口与状态问题，再运行集成层检查。
6. 独立审查 agent 阅读任务、设计和代码，记录可操作的问题。修复后复验并保留验证限制。
7. 更新任务看板和用户文档，按实际证据交付代码、网页或 APK。

## 委派消息的最小内容

```text
任务：HC-XXX / 工作包名称
目标：要实现的可观察行为
范围：允许修改的文件或目录；共享文件由谁负责
接口：输入、输出、错误处理与数据兼容约定
依赖：等待什么；哪些部分可独立推进
验证：需要验证的行为、执行方式与完成条件
反馈：修改、结果、风险 / 限制、待集成事项
```

合同内容同步到任务文档。仅在消息中提出的接口变动，由主 agent 补入记录后再交给依赖方。

## 文件所有权与交接

共享目录中的修改立即可见，不等于已完成集成。任务文档列出每个工作包的写入范围；同一文件需要多人修改时，先交还所有权或由主 agent 汇总修改。

交接包含可复验的结果，不仅是“已完成”。测试未执行、仅用 mock、构建未成功或没有设备，都要说明。任务状态用于表达证据，不据此猜测功能已可用。

## 本项目的真实案例

[HC-001 离线 Android](tasks/HC-001-offline-android.md) 中，存储 agent 实现仓库，平台 agent 实现原生接口，主 agent 集成并构建，独立 agent 审查。审查发现首次读失败可能覆盖旧数据、异步切换时输入丢失和 PNG 元数据错配，均修复并复验，详见 [审查记录](reviews/HC-001-offline-android.md)。

该案例是事后按真实过程整理，并不声称此前每一步都已经有文档。当前 APK 的设备安装与功能验收分开追踪，参见 [安装任务](tasks/HC-003-device-install.md)。
